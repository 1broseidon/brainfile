# CLI/core boundary discovery — thin-frontend refactor spec

> Generated 2026-08-11 by single-agent Sonnet discovery workflow. Source data verbatim from code reading; no code executed.

## Assessment

The cli/core boundary in this repo is inverted from the stated goal: @brainfile/core is a genuinely rich, well-designed library for the V1 (embedded-board) architecture — parsing, serialization, validation, linting, immutable board operations, queries, ID generation, a dependency-graph solver, a ledger, and realtime diffing are all already exported and directly reusable by any frontend. But for the V2 per-task-file architecture, which is what the product actually runs on today (add.ts and others now assert V2-only), core only provides low-level primitives (readTaskFile/writeTaskFile/readTasksDir/generateNextFileTaskId) plus a handful of complete higher-level functions (addTaskFile, moveTaskFile, completeTaskFile, the contract-transition family). Every other V2 mutation — patch, subtask add/delete/toggle/update, the column-resolution+position+auto-complete logic that a real "move" needs, and any form of ranked search — has no core home at all, so it gets hand-rolled independently in cli/src/commands/*.ts, cli/src/mcp/tools/*.ts, and cli/src/tui/actions.ts. The result is not just code duplication but observable behavioral drift between frontends: the TUI's move action never auto-completes tasks landing in a completion column while the CLI command and MCP tool both do; the MCP subtask tool generates new subtask IDs with a different algorithm than the CLI subtask command; and at least four independent, mutually-inconsistent search-ranking implementations exist, none of which call core's own (much simpler) search functions.

Beyond the V2-mutation gap, the review found a smaller but very concrete category of pure accidental duplication: cli/src/commands/contract.ts hand-copies core's entire topologicalSort/MissingDependencyError/DependencyCycleError implementation nearly verbatim instead of importing it, and cli/src/utils/board-types.ts and cli/src/utils/strict-validation.ts duplicate (one exactly, one via a now-dead require()-feature-detection fallback) functions core has already been exporting from index.ts for some time. These are zero-risk, high-confidence fixes that can land before any of the larger V2-mutation-layer work and immediately validate that the consolidation approach works end-to-end.

The path to "cli is a thin frontend" is therefore not a light trim — it requires designing and adding a genuinely new layer of core API (V2-equivalents of the V1 board-operations family, plus a unified ranked-search function) informed by reconciling 2-3 already-diverged implementations of each operation, not just moving existing code verbatim. The ordered phases below start with the zero-risk duplicate deletions, then tackle the V2-mutation-layer gap module by module (keeping the 782-test suite green at each single-file swap), then the higher-judgment-call consolidations (search ranking, contract activate/attach, archive-to-external-service) where a user-visible behavior decision has to be made explicitly rather than accidentally inherited from whichever copy happens to survive.

- Templates: BUILT_IN_TEMPLATES, generateTaskId/generateSubtaskId, processTemplate, getTemplateById/getAllTemplateIds (core/src/templates.ts)
- Completed-task references: taskToCompletedRef, ledgerRecordToCompletedRef (core/src/completed.ts)

## Module verdicts

### move-to-core (14)

**`cli/src/commands/complete.ts`** — `brainfile complete` — V1 completion via findCompletionColumn+moveTask; V2 (completeV2) reimplements epic child-task validation/force-override and writes markdown into logs/ directly.
  - completeV2's helper functions assertSafeTaskId, appendBodySection, extractEpicChildTaskIds, resolveChildTaskStates/resolveParentLinkedChildStates/resolveEpicChildStates, buildChildTasksSection are near line-for-line duplicates of core/src/taskOperations.ts's appendBodySection/extractEpicChildTaskIds/resolveChildTasks/buildChildTasksSection/completeTaskFileLegacy, but the CLI copy is older (writes via plain writeTaskFile with no EEXIST/'wx' exclusivity, no rollback) and adds an epic-incomplete-children force-check that core's completeTaskFile has no equivalent of at all. Should call core completeTaskFile(taskPath, logsDir, {legacyMode:true,...}) and push the force/--force blocking behavior into core as an option so every frontend gets the same epic-safety check.

**`cli/src/commands/add.ts`** — `brainfile add` — builds a V2 task file directly (createV2TaskFile: ID gen, subtask array build, contract attach, parent/child linking) instead of calling core addTaskFile.
  - createV2TaskFile (L99-146) duplicates core addTaskFile's task-construction logic (same field list) but skips the exclusive-write + ID-collision retry loop that addTaskFile provides, and adds parent/child (--child) creation which core has no concept of at all. The parent+children-in-one-shot flow is genuinely new, reusable domain logic that belongs in core (e.g. an addTaskFileWithChildren helper), and add.ts should otherwise call core's addTaskFile directly.

**`cli/src/commands/patch.ts`** — `brainfile patch` — V1 via core patchTask; V2 (patchCommandV2, not fully read but same import/isV2 branch shape as move/subtask) mutates the task object fields directly and calls writeTaskFile.
  - Same recurring shape confirmed via imports (isV2/getV2Dirs/findV2Task + direct writeTaskFile) as move.ts/subtask.ts/task_patch_tool.ts. Core has no V2-equivalent of patchTask; this file-level field patching (including null-to-delete semantics) is duplicated again in cli/src/mcp/tools/task_patch_tool.ts.

**`cli/src/commands/search.ts`** — `brainfile search` — implements its OWN scoring function (scoreMatch/scoreMatchV1: title-start-match, exact-ID-match, tag match, description/log match) independent of core's plain-substring searchTasks/searchTaskFiles.
  - This is the 3rd-5th of 5 independent reimplementations of essentially the same ranked-search algorithm found in this codebase (also in cli/src/mcp/tools/search_tool.ts's inline V1/V2 scoreDoc, and cli/src/commands/log.ts's searchLogs full-text variant). None call core's searchTasks/searchTaskFiles/searchLogs, which only do boolean substring matching with no ranking. A single core `scoreSearchMatch`/`rankedSearch` function would collapse 4+ divergent copies and give every frontend (including a future web UI) the same ranking quality the CLI/MCP users get today.

**`cli/src/mcp/tools/task_add_tool.ts`** — `task_add` MCP tool: V2 branch reimplements addTaskFile's whole body (ID gen, subtask build, task construction) using generateNextFileTaskId + plain writeTaskFile (not the exclusive-write addTaskFile core uses); V1 branch calls core addTask/setTaskContract correctly.
  - Confirmed by reading core's addTaskFile (core/src/taskOperations.ts L289-360): it already does ID retry + exclusive ('wx' flag) write to avoid races; this MCP handler bypasses that safety by hand-building the task and calling plain coreWriteTaskFile instead of addTaskFile — a real correctness gap, not just duplication. Should call core addTaskFile directly, and the with_contract attach-after-create logic should move into core as an option/second call pattern shared with commands/add.ts.

**`cli/src/mcp/tools/task_move_tool.ts`** — `task_move` MCP tool: V2 branch reimplements column-resolution + position calc + auto-complete-on-completionColumn (near-identical to commands/move.ts's moveCommandV2), batch move support.
  - Same finding as commands/move.ts — this is the 2nd of 3 divergent copies of the same move-with-auto-complete algorithm (3rd is tui/actions.ts moveTaskAction, which is missing the auto-complete step entirely, a real cross-surface behavior gap). Consolidate into one core function.

**`cli/src/mcp/tools/task_patch_tool.ts`** — `task_patch` MCP tool: V2 branch mutates task fields (with null-to-delete semantics) directly via coreWriteTaskFile; V1 branch correctly uses core patchTask/patchTasks.
  - Same V2-file-mutation gap as commands/patch.ts — no core equivalent of patchTask for the file-based architecture exists, so this logic (and its null-to-delete field semantics) is duplicated between the CLI command and this tool.

**`cli/src/mcp/tools/list_tasks_tool.ts`** — `list_tasks` MCP tool — filters board tasks by column/tag/type; V1 and V2 branches hand-roll nearly identical filter loops instead of using core's getTasksByTag or a combined filter helper.
  - Core already exports getTasksByTag/getTasksByPriority/getTasksByAssignee individually but has no combined column+tag+type filter, so this tool (and its V1/V2 duplication within the same file) reimplements the combination inline. A core `filterTasks(board, {column, tag, type})` would remove ~35 duplicated lines and give the same filtering to any future frontend.

**`cli/src/mcp/tools/search_tool.ts`** — `search` MCP tool — implements its own title/description/tag/id scoring algorithm (score += 10/5/3/20 weights) across V1 board and V2 board+logs, plus separate `recent` and `task` lookup actions.
  - This is the search-scoring duplication described under commands/search.ts — one of (at least) 4 independent copies of essentially the same ranking heuristic across this codebase, none of which call core's plain-substring searchTasks/searchTaskFiles/searchLogs. Prime consolidation target.

**`cli/src/mcp/tools/subtask_tool.ts`** — Unified `subtask` MCP tool (add/toggle/delete/update, single/array/all targeting) — V2 branches hand-roll subtask ID generation (`Math.max(...ids)+1`, DIFFERENT algorithm from core's generateNextSubtaskId used by commands/subtask.ts), array/set mutation, and writeTaskFile calls, entirely independent of the V1 board-operations import used for the V1 branch.
  - Confirmed against cli/src/commands/subtask.ts's V2 path, which instead calls core's generateNextSubtaskId — meaning this MCP tool and the CLI command generate new subtask IDs via two DIFFERENT algorithms for the same file format, a genuine consistency risk. There is no core V2-file equivalent of addSubtask/deleteSubtask/updateSubtask/toggleSubtask/setSubtasksCompleted/setAllSubtasksCompleted at all; adding one (operating on Task via readTaskFile/writeTaskFile, mirroring the V1 board operations already in core/src/operations.ts) would remove ~250 lines of duplicated mutation logic between this file and cli/src/commands/subtask.ts.

**`cli/src/utils/dot-brainfile.ts`** — ensureDotBrainfileGitignore (mkdir + read/filter/write .gitignore, stripping legacy `state.json` lines) + removeLegacyStateFile.
  - Direct duplication confirmed by side-by-side read against core/src/utils/files.ts's ensureDotBrainfileGitignore/getDotBrainfileGitignorePath, which already does mkdir+gitignore-write (core's version just doesn't do the legacy-line-stripping). Callers (commands/init.ts, commands/migrate.ts) should use core's ensureDotBrainfileGitignore; the removeLegacyStateFile legacy-cleanup helper is small enough to fold into core too (or delete once no workspace still has state.json — worth confirming with the user before removing).

**`cli/src/utils/archive.ts`** — Local-file archive read/write: getArchivePath, loadArchivedTasks, archiveTaskToFile, removeFromArchive, restoreFromArchive — manages a separate `<board>-archive.md` V1-format board file.
  - This is pure fs read/parse/serialize/write logic over a Board (same shape as core's boardFile.ts), scoped to the V1 archive feature; a web/electron frontend implementing 'archive to local file' would want the exact same functions. Low risk to promote since it only depends on Brainfile.parse/serialize already in core.

**`cli/src/utils/contractSpec.ts`** — parseDeliverableSpec/buildContract — parses `type:path:description` CLI strings into Contract deliverable objects and assembles a full Contract from CLI flag arrays.
  - buildContract is called identically from commands/add.ts, commands/contract.ts, mcp/tools/task_add_tool.ts, and mcp/tools/contract_tool.ts — already a de-facto shared dependency living in cli/src/utils instead of core; the `type:path:description` string format is a public, documented contract format (per CLAUDE.md's 'Deliverable format' section) that any frontend building a contract-creation UI would need to parse/build the same way.

**`cli/src/tui/utils.ts`** — parseSearchQuery (structured query-string mini-language: p:high, t:bug/#tag, @assignee, due:overdue/today/week/month, contract:ready) + taskMatchesFilter (applies parsed filter to a Task) + truncate/getPriorityColor.
  - This is the richest of the 5 search/filter implementations found in the codebase and the ONLY one with structured filter syntax (priority/tag/assignee/due-date/contract-status prefixes) — yet it's trapped in the TUI only, meaning cli/src/commands/search.ts and the MCP `search` tool don't offer this filtering language at all, a real feature-parity gap directly caused by the lack of a shared core query layer. Promoting parseSearchQuery+taskMatchesFilter to core (operating on Task, no fs/ink dependency) would let CLI `search` and the MCP `search` tool gain the same filter syntax for free.

### split (12)

**`cli/src/commands/move.ts`** — `brainfile move` — V1 board move via core moveTask; V2 (moveCommandV2) hand-rolls column-id-or-name resolution, position calc via readTasksDir, private getBoardTypes/isTaskCompletable duplicate, and auto-complete-on-completionColumn by calling core completeTaskFile.
  - V2 path (lines 177-258) reimplements exactly the logic core's moveTaskFile lacks (column resolution, position, auto-complete). Confirmed byte-level duplicate of this same logic also appears in cli/src/mcp/tools/task_move_tool.ts and a third, less complete variant in cli/src/tui/actions.ts moveTaskAction (no auto-complete there — a real cross-frontend behavioral inconsistency). Move the column-resolve+position+auto-complete orchestration into a new core function (e.g. moveTaskFileToColumn); keep chalk/console output and CLIError throwing in cli.

**`cli/src/commands/log.ts`** — `brainfile log` — view/append task logs; searchLogs() here is a 5th independent full-text log search implementation (title/description/log-body substring match with match-context line extraction), separate from core's searchLogs and from commands/search.ts's scoring.
  - logCommand/logNoteCommand (append a note to a task body) is presentation-adjacent CLI plumbing over core appendLog — stay-cli. searchLogs (L174-235) duplicates yet another search variant and should be folded into the same core ranked-search consolidation as commands/search.ts and mcp/tools/search_tool.ts.

**`cli/src/commands/init.ts`** — `brainfile init` — scaffolds a new .brainfile/brainfile.md from a hardcoded V2 template string; calls utils/dot-brainfile.ts's ensureDotBrainfileGitignore/removeLegacyStateFile instead of core's equivalent.
  - The scaffolding/template-writing is fine to stay in cli (it's an interactive `init` wizard). But it calls the CLI-local utils/dot-brainfile.ts duplicate of core's ensureDotBrainfileGitignore (see duplications) — should switch to core's version, which already does the same job with clearer semantics.

**`cli/src/commands/adr.ts`** — `brainfile adr` — promotes a task's description into an 'always' rule entry; has its own assertSafeTaskId, readBoard/writeBoard, parseRuleId/getNextRuleId helpers.
  - readBoard/writeBoard here is yet another copy of the Brainfile.parseWithErrors+fs read/write boilerplate (5th+ occurrence — see duplications). The actual rule-ID-generation/promotion logic (parseRuleId, getNextRuleId, extractRuleText) is genuine domain logic not present in core (core's addRule takes pre-built rule text, doesn't do 'promote a task into a rule' semantics) and is a reasonable move-to-core candidate for consistency with core's addRule/deleteRule family.

**`cli/src/commands/types.ts`** — `brainfile types` — manage board.types config (add/list/remove custom types) directly via yaml read/write of the board config frontmatter.
  - Confirmed via imports (js-yaml, readV2BoardConfig) this hand-edits board config YAML for a feature (custom type registry) that overlaps with core's boardValidation.ts (getBoardTypes/validateType) but core has no *mutation* API for board.types at all — a `updateBoardTypes`-style core function would remove this hand-rolled YAML editing from cli.

**`cli/src/commands/archive.ts`** — Local/GitHub/Linear task archiving: archiveSingleFromLogsV2/archiveAllFromLogsV2 (local), archiveToGitHub/archiveToLinear (build payload via core formatters, call github-auth/linear-auth network functions, then delete the local task).
  - The local-archive fs operations (write to archive board / logs) mirror core's file-write patterns and could be core functions (utils/archive.ts already partially does this — see below). The GitHub/Linear orchestration (payload-build -> API-create -> local-delete) is duplicated near-verbatim in cli/src/mcp/tools/task_complete_tool.ts (same 4-branch destination === 'github'/'linear' logic, same team-resolution fallback) — a shared `archiveTaskExternally(task, destination, config)` orchestrator (calling out to injectable auth/create functions) would remove ~150 lines of duplication between these two files, though the OAuth/auth-store portion should stay CLI-specific.

**`cli/src/mcp/helpers.ts`** — Shared MCP helpers: sanitizeTypesConfig/isTaskCompletable (board.types completability rules), readBoard/writeBoard (V1 board read/write via core buildBoardFromV2/Brainfile.serialize), mcpStructuredError, findGitRoot.
  - sanitizeTypesConfig/isTaskCompletable is genuine board.types domain logic duplicated a 3rd time (also inline in cli/src/commands/move.ts's private getBoardTypes/isTaskCompletable, and separately in cli/src/utils/board-types.ts which just re-wraps core's already-exported getBoardTypes) — should collapse to one core function (e.g. core's existing getBoardTypes plus a new isTypeCompletable). readBoard/writeBoard are thin and fine as an MCP-local convenience; mcpStructuredError/findGitRoot are legitimately MCP-transport/environment concerns and stay-cli.

**`cli/src/mcp/tools/task_complete_tool.ts`** — `task_complete` MCP tool — default path delegates to cli's own commands/complete.ts completeCommand (cross-layer import of a 'cli command' from 'mcp', itself a smell); destination=local/github/linear paths reimplement local-archive and GitHub/Linear issue-creation orchestration independently of commands/archive.ts.
  - The delegation to completeCommand shows the CLI command layer already contains logic the MCP layer needs — evidence the completion logic belongs one level down, in core, not in cli/src/commands. The github/linear archive branches (payload build via core formatters + auth check + issue create + local delete) are near-duplicate of cli/src/commands/archive.ts's archiveToGitHub/archiveToLinear — consolidate into one orchestrator function; keep the interactive OAuth/auth-store calls as CLI-injected dependencies.

**`cli/src/mcp/tools/contract_tool.ts`** — Unified `contract` MCP tool (attach/pickup/deliver/validate/graph/activate) — attach and activate actions hand-roll contract mutation (buildContract + direct task.contract assignment + metrics.readyAt stamping) for both V1 and V2, duplicated against cli/src/commands/contract.ts's contractAttachCommand/contractActivateCommand; pickup/deliver/validate correctly delegate to cli/src/lib/contractRunner.ts.
  - pickup/deliver/validate/graph are already thin (call contractRunner.ts / commands/contract.ts's contractGraphCommand via mcp/tools/contract.ts) — good pattern to replicate. attach and activate (L58-110, L187-308) directly mutate task.contract and stamp metrics.readyAt inline rather than calling a shared function; this exact 'draft→ready + metrics.readyAt' transition logic needs to be checked against commands/contract.ts's contractActivateCommand (L720-866, not fully read but same shape) — high suspicion of a 3rd/4th duplicate given the pattern elsewhere in this codebase; recommend a core `activateTaskContract`/`attachTaskContract` (V1+V2) pair.

**`cli/src/commands/contract.ts`** — CLI contract commands: contractPickupCommand/contractDeliverCommand/contractValidateCommand (delegate to lib/contractRunner.ts, thin), contractAttachCommand (direct contract build+attach), contractActivateCommand (draft->ready transition), contractGraphCommand (batch-attach with dependsOn DAG); ALSO independently redefines DependencyGraphNode/MissingDependencyError/DependencyCycleError/topologicalSort/normalizeDependencyIds.
  - Lines 150-257 (topologicalSort and its two error classes) are a near-verbatim, hand-copied duplicate of core/src/graph.ts's exported topologicalSort/MissingDependencyError/DependencyCycleError — confirmed by side-by-side read, the two implementations are functionally byte-identical modulo minor type-signature differences (readonly string[] vs string[]). This should simply `import { topologicalSort, MissingDependencyError, DependencyCycleError } from '@brainfile/core'` and delete the local copy — the single highest-confidence, zero-risk duplication fix in the whole codebase. contractAttachCommand/contractActivateCommand contain the same attach/activate mutation logic seen duplicated in mcp/tools/contract_tool.ts — move-to-core candidates alongside that finding. contractGraphCommand's argument parsing (parseContractGraphArgs) is CLI-flag-specific and should stay.

**`cli/src/utils/errorHandler.ts`** — ExitCode/ErrorType enums; isDoneColumn (regex heuristic near-duplicate of core findCompletionColumn's inline pattern list) + checkIncompleteSubtasks/getIncompleteSubtasksWarning (task-level incomplete-subtask summary + warning text) + *Error() CLI formatters + mcpError/mcpCheckIncompleteSubtasks (MCP-flavored duplicates of the same warning).
  - checkIncompleteSubtasks/getIncompleteSubtasksWarning is genuine, reusable domain logic (not just formatting) currently duplicated in spirit via mcpCheckIncompleteSubtasks (same file) for the MCP text format, and needed by both commands/move.ts and mcp/tools/task_move_tool.ts — should become a core function (e.g. getIncompleteSubtasksSummary(task)) returning structured data, with cli/mcp formatting the human-readable warning text themselves. isDoneColumn's DONE_COLUMN_PATTERNS list is a near-duplicate of core findCompletionColumn's inline completionPatterns (both matching done/complete*/finished/closed via regex against id/title, but with different anchoring — `^done$` here vs `/done/` in core) — should reuse core's pattern via findCompletionColumn/isCompletionColumn instead of a separate regex list. The Error()/ExitCode formatters themselves stay CLI.

**`cli/src/tui/actions.ts`** — ~1400 lines of TUI keybinding-triggered actions: moveTaskAction (calls core moveTask/moveTaskFile directly — best-aligned of the three move implementations, but skips the auto-complete-on-completionColumn step that CLI/MCP both do), deleteTaskAction, archiveTaskAction(+Async), patchTaskAction, cyclePriorityAction, toggleSubtaskAction, addTaskAction, newTaskInEditor/editTaskInEditor ($EDITOR round-trip via temp YAML files), addRuleAction/updateRuleAction/deleteRuleAction, loadLogs, restoreTaskAction, deleteArchivedTaskAction.
  - This is the 3rd independent surface (after cli commands and MCP tools) implementing move/patch/add/delete/toggle-subtask/rule-CRUD, and it's the clearest evidence of the core cross-frontend inconsistency risk: moveTaskAction here does NOT auto-complete when moved to a completion column (confirmed by reading L132-167), while cli/src/commands/move.ts and mcp/tools/task_move_tool.ts both DO — a real behavior divergence a user would hit depending on which interface (terminal command vs TUI vs MCP agent) they used. cyclePriorityAction/toggleSubtaskAction/patchTaskAction/addTaskAction should all be replaced with calls to the same consolidated core V2-file-mutation functions proposed for commands/*.ts and mcp/tools/*.ts. newTaskInEditor/editTaskInEditor (spawn $EDITOR, parse round-tripped YAML) and copyToClipboard are genuinely TUI-interaction-specific and stay-cli.

### delete-dead (2)

**`cli/src/utils/board-types.ts`** — getBoardTypes(board) — reads board.types, defaulting to {}.
  - Verbatim duplicate of core/src/boardValidation.ts's getBoardTypes, which is ALREADY exported from @brainfile/core's index.ts. Every caller of this file's getBoardTypes should switch to the core export and this file deleted — confirmed no functional difference between the two implementations.

**`cli/src/utils/strict-validation.ts`** — validateType/validateColumn — feature-detects core's validateType/validateColumn via `require('@brainfile/core')` and falls back to a hand-duplicated implementation if core doesn't export them.
  - Core has exported validateType/validateColumn from index.ts for a while (confirmed present in current core/src/index.ts and core/src/boardValidation.ts) — the runtime feature-detection branch is now permanently truthy, making the ~25-line fallback implementation (lines 20-36, 44-56) dead code that only adds confusion and an unusual `require()` call in an otherwise ESM/import codebase. ## Implementation phases (smallest-risk first)

### Phase 0 — Zero-risk dead-code and re-export cleanup

Delete cli/src/utils/board-types.ts and cli/src/utils/strict-validation.ts's fallback branches, switching their few callers to import getBoardTypes/validateType/validateColumn directly from @brainfile/core. ### Phase 2 — Add the missing V2 file-mutation core layer (the big one)

## Risks

- The V1 (embedded-board) code path is still fully implemented in parallel with V2 across nearly every command and MCP tool (move, patch, complete, add, subtask, contract, search, list, show, rules, archive, adr all branch on isV2(filePath)), even though several commands (add.ts, patch.ts via assertV2Brainfile pattern elsewhere) already treat V1 as unsupported. Any core consolidation work has to decide, file by file, whether to keep maintaining two parallel APIs (V1 board-based + V2 file-based) or use this refactor as the moment to deprecate V1 support outright — doing both halfway is exactly how the current duplication accumulated.
- core/src/taskOperations.ts's completeTaskFile has TWO modes (ledger-record mode by default, legacyMode:true for markdown-to-logs/) that already don't match what cli/src/commands/complete.ts's completeV2 actually does (writes markdown to logs/ unconditionally, which is legacyMode behavior, but was reimplemented rather than calling completeTaskFile({legacyMode:true})) — before consolidating, confirm with the team which completion behavior (ledger vs markdown-in-logs) is actually the intended current product behavior, since the CLI, MCP, and core disagree today.
- Three frontends (CLI command, MCP tool, TUI action) currently disagree on whether moving a task to a completionColumn should auto-complete it (TUI's moveTaskAction does not; CLI move.ts and MCP task_move_tool.ts do). Consolidating into one core function forces a decision on which behavior is correct — this is a user-visible behavior change for whichever surface currently has the 'wrong' one, not a pure refactor.
- mcp/tools/subtask_tool.ts and commands/subtask.ts use two different subtask-ID-generation algorithms; unifying onto core's generateNextSubtaskId could change generated IDs for edge cases (non-sequential or non-numeric existing subtask ID suffixes) relative to what the MCP tool currently produces — needs a compatibility check against any existing boards with subtask IDs generated via the MCP tool's Math.max approach.
- core's published API is additive-only per the task's constraint, but several proposed new exports (moveTaskFileToColumn, patchTaskFile, subtask-file mutators, searchTasksRanked) will need to decide their own error-handling convention (throw vs {success,error} return) — core currently mixes both styles (V1 board operations return {success,error}; parser/validator throw or return null). Picking one convention for the new V2-file functions, ideally matching the existing addTaskFile/moveTaskFile {success,error} style, avoids yet another inconsistency being introduced during the fix.
- Phase 5 (archive-to-GitHub/Linear orchestration) would be core's first function with a network-I/O dependency; today core is a pure fs+parsing library with zero runtime dependencies beyond js-yaml-style parsing. Moving network orchestration into core changes that dependency profile and may not be desired — flagged as optional/last and explicitly deferred pending a product decision rather than assumed.
- This review reads the current tree only; it does not execute the 782-test suite, so verdicts on 'safe to consolidate' are based on code-reading (confirmed duplicated logic, confirmed divergent behavior) rather than test coverage confirmation — each phase above explicitly calls for running the full suite after every single-file migration, not just at the end of a phase.
